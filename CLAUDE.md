# synthea-readmission-risk

Predicts unplanned 30-day hospital readmission from Synthea-generated synthetic patient records: a PySpark "Big Join"
builds a per-encounter gold table, a leakage-controlled pipeline trains and calibrates two models, and a Top-N triage
CLI ranks held-out discharges for a clinical team lead. See [README.md](README.md) for the public overview.

## Architecture

Locked in via `/eg-prd` on 2026-09-15 — full reasoning, research, and risk analysis in `notes/prds/big-join-architecture-lock-in-2026-09-15.md`. Executes the chosen "Big Join + The Triage List" concept from `notes/eg-brainstorms/readmission-risk-cv-project-2026-09-15.md`.

**Data pipeline (staged, to protect the "weeks not months" timeline):**
1. **Local proving phase:** generate ~10k-20k Synthea patients locally; run the "Big Join" feature-engineering step as local PySpark (`local[*]` master); all data stays on local disk — no GCP dependency at this stage.
2. **Scale-up phase:** once the pipeline is correctness-proven locally, run the *same* PySpark job (only a config-driven base path changes, not a rewrite) on Dataproc Serverless against GCS-resident data at ~50k-100k patients.
3. **Serving layer:** BigQuery holds only the gold table (patient-encounter features + risk score), written via the `spark-bigquery-connector`'s **direct write method** (BigQuery Storage Write API) — not the indirect GCS-staging-bucket path, to avoid provisioning a bucket purely for the BigQuery load. Raw/intermediate data stays in GCS, never loaded into BigQuery, to stay inside BigQuery's free storage tier. **Amended for v2 (2026-10-09):** BigQuery also holds `predictions`, `scoring_runs` and `monitoring` (plus a call-sheet view); raw/intermediate data still stays in GCS; see "v2 architecture" below.

**Stack:**

| Layer | Choice |
|---|---|
| Compute | PySpark — local mode for dev, Dataproc Serverless for scale-up |
| Warehouse | BigQuery: gold only in v1; v2 adds `predictions`, `scoring_runs`, `monitoring` (see "v2 architecture") |
| Dependency management | `pip` + `requirements.txt`, generated via `pip-compile --generate-hashes` (pip-tools), installed with `pip install --require-hashes` |
| Python version | **3.14** locally (`.python-version` 3.14.7, since 2026-10-09); CI tests **3.14**, plus `tests/pipeline` on the Dataproc-runtime-3.0 mirror (3.12 + PySpark 4.0.2 since 2026-10-12, 4.0.1 from v2 slice 1); `requires-python = ">=3.12,<3.15"` — see note below |
| Testing | `pytest` + `chispa` (or PySpark 4.1+'s built-in `assertDataFrameEqual`) for DataFrame-equality assertions; transformation/join logic factored into pure functions so it's testable independent of local-vs-cloud environment |
| Schema handling | Hand-declared `StructType` per Synthea CSV table — never `inferSchema` |

Found and fixed along the way: `make_spark_session` did not pin the Python workers' interpreter, so PySpark fell back to `python3` on `PATH` (pyenv's, 3.12) and every Python task failed with `PYTHON_VERSION_MISMATCH` under a 3.14 driver; it now defaults `PYSPARK_PYTHON` to the driver's `sys.executable` (an explicit setting still wins), with a regression test in `tests/pipeline/test_spark_session.py`. **Hard constraint carried into future model-training work:** the train/test split for the readmission model must be chronological (by admission/discharge date) and grouped by patient ID — never a random row-level split — per this project's standing reproducibility/leakage-prevention rule (see Collaboration preferences above). **Resolved 2026-09-19 (slice 3, `notes/eg-new-feature/model-training-2026-09-19.md`)** in `src/readmission_risk/models/split.py`: a chronological split at a caller-chosen `--test-start-date` (2023-01-01 for the reference run) that is ALSO patient-disjoint (train rows of any patient who appears in the test window are dropped), with a censoring buffer (`index_stop + 30d < reference_date + 1d`, slice 2's own observability rule applied to positives too, removing the asymmetry slice 2 left) and a label-window purge (train rows whose 30-day outcome window reaches into the test period are dropped). Slice 3 also enforces the leakage rules structurally: every fitted statistic lives in a `Pipeline` fitted on training rows only; inner calibration folds are patient-grouped; `organization_utilization` (a whole-simulation total, not point-in-time) and the constant `provider_specialty` are excluded from the features, and a test fails if any gold column is left unclassified. Since 2026-10-10 a label-horizon purge (step 4b, after the label-window purge) also drops train rows whose label depends on any record dated on or after the test start (see caveat (4) below).

**Slice-3 results caveats, carried forward and re-measured on the slice-2b gold table (2026-09-20)** (figures live in `docs/results.md` and `notes/eg-new-feature/readmission-label-planned-exclusion-2026-09-20-measurements.md`, not here; the slice-3 design doc's own numbers describe the pre-2b all-cause table): (1) the 2023+ test window is NOT a virgin holdout — prototypes scored these models on it during design and the cutoff, feature and (now) label-rule choices were all made from this data (the third such decision); report its metrics as development-set quality, and use the v2 population (generated with a NEW seed and fresh `reference_date`, and sized for statistical power — see (2)) as the untouched validation. (2) After slice 2b the test window holds only **41 positives (2.66%; train 96, 1.50%)** — below slice 3's 50-positive reliability threshold, so its "unreliable" warning fires on the real run by design (the threshold was not lowered) — and intervals are wide. A reason-code-only lookup (test AUC 0.873) is at least as good as either model: logistic regression 0.869, calibrated XGBoost 0.823 (worse than the lookup and than LR, paired intervals excluding 0); Brier skill scores vs the train prevalence are 0.022 / 0.014. The positive rate shifts between train and test (1.50% vs 2.66%), so the models under-predict on average; do not read that as a defect by itself. The label is still reason-concentrated (test window: CABG-history 23 of 41) — fixed 24-hour post-operative stays repeated a median 16.6 days later (a generic procedure bundle but no planned-procedure code; only 1 of the 45 readmissions begins via the ED, versus 27 of 30 for CHF) that the rule deliberately does not classify as planned; whether to iterate the label again is an open decision — four measured label-v2 candidates are in the design note's "Label v2" section, and none leaves more than 18 test positives at 10k patients, so adoption is deferred to the larger population. **Expectation for the v2 (100k–200k) population (a projection, not a measurement; recipe in the slice-2b measurements note):** more data mainly buys measurement precision (≈1,000–2,000 train / 400–800 test positives, intervals ≈3–4× narrower, the reliability warning stops firing) and lets the models catch up to the lookup (in a learning-curve check the lookup is already saturated while LR and XGBoost are still climbing); it is NOT expected to lift AUC much beyond the reason-code ceiling (≈0.87–0.90), because within the large reasons no patient feature separates readmitted from non-readmitted stays — Synthea generates these events from scripted pathways plus random draws. (3) The pre-2b finding that "LR and XGBoost are indistinguishable only under the default training window" no longer holds: XGBoost is worse than LR on ROC-AUC under BOTH the default window and `--train-start-date 20170916` — the latter rests on only 24 training positives and should be read as a direction only. (4) The label now depends on the content of the readmitting stay, not just its start time. **Since 2026-10-10 this is enforced, not measured** (`notes/eg-new-feature/label-horizon-purge-2026-10-09.md`): the Big Join writes a 24th gold column, `label_horizon` (latest record the label depends on: in-window stays' STOP, their planned-procedure dates, earlier stays' STOP; an open stay or undated planned record counts as the end of observation), and the split's step 4b purges train rows with `label_horizon >= test_start`, warns when it drops any, reports `n_dropped_label_horizon_purge`, and a post-condition raises `RuntimeError` if one survives (owner decision: purge + invariant, not fail-the-run, because a hard failure was projected to fire ~20-40% of the time at v2 scale). On this data it purges 0 rows at 2023-01-01 (closest record 2022-12-25T01:59:59Z, ~6.9 days). It guarantees each train row's *label* uses pre-cutoff records only, NOT that the train set's composition does: index-row membership (terminal rule, planned-index exclusion; both 0 on this data) remains a named follow-up. The loader refuses a gold table without the column and the scorer strips it with the label (`LABEL_SIDE_COLUMNS`). The reference runs were retrained on the rebuilt table into `readmission-risk-v1` (Python 3.14.7): identical split assignment, metrics and predictions to the 3.12-trained `readmission-risk-2b` runs, which are kept as history. **Deviations from the MLOps-spine wording above (decisions, not drift):** training reads local Parquet, not BigQuery `to_dataframe()` (BigQuery is the scale-up phase; the loader is one swappable function); `mlflow.autolog()` (one call, spark/pyspark.ml flavors excluded) logs params/in-sample training scoring but the models are logged explicitly with `serialization_format="cloudpickle"` (autolog's default skops format rejects the calibrated XGBoost model) — slice 4 loaded them via `readmission_risk.models.tracking.load_logged_model(tracking_dir, run_id)` (since v2 slice 2 the scorer instead loads the same `model.pkl` bytes from a model bundle with `cloudpickle`; `load_logged_model` remains for training tests, the exporter's oracle and reporting), needs the same lockfile versions, and gets a pickle-safety warning; `LogisticRegression` is not wrapped in `CalibratedClassifierCV` (natively probabilistic; its calibration is evaluated like XGBoost's). **Known gaps (unchanged conventions, flagged not fixed):** `pyproject.toml` still declares `dependencies = []` (the project's lockfile-only convention), and no CI check verifies that `requirements.txt` still matches `requirements.in` (resolved 2026-10-12 by `tests/test_lockfiles.py`; a guard-8 champion-compatibility check is still missing); the earlier gap that `reference_date`/`readmission_window_days` could not be validated against the gold table is **resolved in slice 2b** (`_gold_metadata.json`, checked for exact equality by `train_and_evaluate`; its row/positive-count cross-check cannot detect an edit that preserves both counts — a content fingerprint is a named follow-up). The full list of remaining slice-3 follow-ups (hyperparameter tuning, feature attribution, CI pip cache, a tracked reference-baseline run, fresh-seed v2 validation, the pandas 3 upgrade check, and more) is the design doc's "Out-of-scope follow-ups" section in `notes/eg-new-feature/model-training-2026-09-19.md`.

**Requirement carried into slice 2 (the Big Join feature-engineering design), found empirically 2026-09-17 — resolved 2026-09-19:** local Synthea generation was run with `exporter.years_of_history=0` (full patient history, no truncation) so slice 1 wouldn't pre-judge how much lookback the join needs. This has a real cost — an isolated comparison at the same population/seed showed full history is **~2.6x** the size of Synthea's own 10-year-default export (1.6GB vs 637MB at 1,000 patients), and even the 10-year default extrapolates to ~6.4GB at 10,000 patients, well past the "a few hundred MB" that was informally expected. Two decisions the slice 2 design doc had to make explicitly, not by default — both now resolved and implemented (full reasoning and measurements in `notes/eg-new-feature/pyspark-big-join-2026-09-19.md` and its companion `...-measurements.md`):
1. **History lookback window, resolved as `lookback_years=1` (feature window) + `exporter.years_of_history=10` (regeneration bound).** `lookback_years=1` matches the LACE index's 12-month convention and is empirically supported: a per-calendar-year sparsity analysis of the full-history export found 0.0% of alive patients had zero observations in any calendar year (1916-2025), so a 1-year window isn't degenerate. `years_of_history=10` was chosen (not just because it's Synthea's own default) because it measures to ~2GB at 10,000 patients for the 10 selected tables below — an ~8.5x reduction from the prior 17GB full-history export — while keeping the lookback-window "truncation dead zone" to ~10% of the retained population. Confirmed empirically at BOTH population=1,000 and the real target population=10,000 that active (ongoing) condition/medication/careplan counts are invariant to `years_of_history` (Synthea preserves a patient's full current problem list regardless of history-window setting); only resolved/historical records are pruned.
2. **Table selection, resolved as 10 of Synthea's ~18 exported tables**: `patients`, `encounters`, `conditions`, `medications`, `procedures`, `careplans`, `observations`, `payers`, `providers`, `organizations` (see `TABLES_JOINED` in `src/readmission_risk/pipeline/big_join.py`). `claims.csv`/`claims_transactions.csv` are excluded as billing-line-item exports (confirmed: together ~11GB of the prior 17GB full-history export); `immunizations`/`allergies`/`devices`/`imaging_studies`/`payer_transitions`/`supplies` are excluded as weak/indirect signal for a first-pass readmission model. `generation.py`'s `EXPECTED_CSV_TABLES` was extended from the original 7 to all 10 of these to match; `REQUIRED_NONEMPTY_TABLES` was extended from 2 (`patients.csv`, `encounters.csv`) to 5 (adding `payers.csv`/`providers.csv`/`organizations.csv`) — the other 5 joined tables (`conditions`/`medications`/`procedures`/`careplans`/`observations`) are deliberately allowed to come back empty (warning-only, not a hard failure) per `validate_generation_output`'s existing design — **with one asymmetry added in slice 2b (2026-09-20): the Big Join now hard-fails on an empty `procedures.csv`** (`TABLES_MUST_BE_NONEMPTY`), because the planned-stay flag reads it and an empty file would silently revert the label to (nearly) all-cause; slice 1's `REQUIRED_NONEMPTY_TABLES` still only warns (named follow-up).

**Readmission label (locked 2026-09-19; redefined 2026-09-20 in slice 2b — `notes/eg-new-feature/readmission-label-planned-exclusion-2026-09-20.md`):** an **unplanned** 30-day readmission flag, `is_readmitted` (column name kept; semantics changed; identity `LABEL_DEFINITION = "unplanned_readmission_v1"` in `src/readmission_risk/pipeline/gold_metadata.py`). Inspired by, but not a full implementation of, CMS HRRP's and LACE's shared 30-day convention, which exclude planned readmissions (the CMS specifics are as recalled, not verified — verify before citing). All rules are over inpatient stays: a stay is **planned** if it carries a chemotherapy/radiation procedure (SNOMED 33195004, 367336001, 703423002) — on Synthea data this identifies the lung-cancer treatment cycles that were 72.6% of the old all-cause positives; a stay is a **continuation** if it starts at or before the end of an earlier stay of the same patient (Synthea records one surgical care episode as several overlapping encounters); a stay is **terminal** if no other same-patient stay has `START <= its STOP < that stay's STOP`. Index encounters = inpatient stays with a non-null `STOP` that are neither planned nor non-terminal; label = 1 if the same patient has a stay that is neither planned nor a continuation starting in `(STOP, STOP + 30d]` (upper bound inclusive); an index is excluded entirely (not labeled 0) when the patient died or the export's observation window ended before a readmission could be confirmed absent (applied AFTER labeling). Known residuals (see the design note): CABG-history recurrences (fixed 24-hour post-operative stays with no planned-procedure code) and CHF recurrences remain positives (four measured label-v2 candidates: design note, "Label v2"); features stay stay-level, not episode-level. `build_big_join` also writes `_gold_metadata.json` next to the Parquet (label definition, planned codes, `reference_date`, window, lookback, row/positive and stay-flag counts) and slice 3 **refuses** a gold table without it or with a mismatching `reference_date`/`readmission_window_days`. See `flag_inpatient_stays` / `build_index_encounters` in `src/readmission_risk/pipeline/big_join.py`. (Superseded definition, kept for history in the slice-2 design doc: all-cause, no planned exclusion.)

**Slice 4 — Top-N triage CLI, a DEMO over held-out gold rows (2026-09-20; design and 5-round design check in `notes/eg-new-feature/batch-scoring-cli-2026-09-20.md`).** `scripts/score_discharges.py` (Typer, no logic; `typer==0.27.2` is now a runtime pin in `requirements.in`/`requirements.txt`, adding `rich`, `markdown-it-py`, `mdurl`, `shellingham`, `pygments`) is a thin layer over the pure functions in `src/readmission_risk/scoring/` (`constants`, `selection`, `bundle_guard` (was `runs` until v2 slice 2), `ranking`, `store`, `report`, `pipeline`; `tests/scoring/` mirrors it; the scorer must never import `pipeline.big_join`, and since v2 slice 2 it imports neither mlflow nor pyspark, enforced by a subprocess test and a static test in `tests/scoring/test_pipeline.py`). It scores the discharges (`index_stop`) of a trailing window of W UTC calendar days ending on `--run-date` (default W = the gold table's readmission window, 30), restricted to the chosen model's own `split_assignment.csv` **test** partition; a window containing any train/dropped/censored row is refused (no override), a window past the observation horizon (reference date minus the label window; slice 2 keeps non-readmitted discharges only once their outcome window has closed, so later windows would be silently truncated) is refused too; on the real table that leaves run dates 20230208-20260817. 14 guards refuse a mismatched model before it is unpickled (cloudpickle can execute code on load); **since v2 slice 2 (`notes/eg-new-feature/v2-slice2-model-bundle-and-manifest-2026-10-11.md`) they read a model bundle's `manifest.json` in `scoring/bundle_guard.py::validate_bundle`, after integrity checks I1-I5, instead of an MLflow run in the deleted `scoring/runs.py`**: finished/non-deleted, `model_uri`, `model_name`, `gold_label_definition`, `gold_fingerprint` (trained on exactly this gold table), `reference_date`/`readmission_window_days`, library versions, `feature_columns.json`, model signature, `split_assignment.csv`, split consistency against the run's `test_start_date` and gold, and the model's own `run_id`, and the Python major.minor (guard 14). Output: `data/predictions/run_date=YYYYMMDD/predictions.parquet` (gitignored), the full ranked batch (`rank`, `is_top_n`, ties broken by `encounter_id` ascending), no label column, replaced as a unit per run date; the observed label is only an opt-in stdout summary (`--show-observed-outcomes`), joined after scoring. `store.write_partition` is the only storage-aware function and `score_run_date(config, *, loader, writer)` takes it as an injection point: that is the seam for the BigQuery direct-write swap. **Named follow-ups (not built):** the as-of scoring path (features for unlabelled recent discharges from the raw CSVs, open-stay semantics — `flag_inpatient_stays`' null-`STOP` handling must change, do not reuse it — and a scoring-side eligibility filter), label v2 (after the 100k-200k scale-up), `DEMO_NOTICE` is dataset-specific and must be revisited for the v2 population, the BigQuery/dashboard consumers, `[project.scripts]`, and a tests/conftest.py hoist of the MLflow-state fixture (the session `scoring_env` fixture itself moved to `tests/conftest.py` in v2 slice 2; the per-package MLflow-state guards did not). **Design-check note:** the doc's critic pass never formally closed on the final revision (readiness did, in round 5); the user authorized proceeding, and every late fix is exercised by tests.

**MLOps spine (locked 2026-09-15, second `/eg-prd` pass):**
- **Models:** scikit-learn `LogisticRegression` baseline + `XGBClassifier` (XGBoost) challenger, both trained on the BigQuery gold table via `google-cloud-bigquery`'s `to_dataframe()`. Both MUST report calibrated probabilities (`CalibratedClassifierCV` on the XGBoost model) and MUST be evaluated on calibration curve + Brier score alongside AUC — "calibration over raw accuracy" is a project priority given synthetic data, not accuracy/AUC alone.
- **Experiment tracking:** MLflow, **local file-store/SQLite backend for v1** (zero infra, `mlflow.autolog()` covers both models in one call). A hosted GCP tracking server (Cloud Run + Cloud SQL + GCS) is a named **later-phase upgrade**, not v1 scope.
