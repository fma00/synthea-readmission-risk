## Working with Claude Code (slash commands)

Five slash commands in [.claude/commands/](.claude/commands/) wrap an "elephant/goldfish" workflow inspired by [this article](https://drensin.medium.com/elephants-goldfish-and-the-new-golden-age-of-software-engineering-c33641a48874): the "elephant" is the working session with full context (this CLAUDE.md, repo state, conversation history); the "goldfish" is a fresh subagent with no prior context. For implementation work the goldfish stress-tests a problem/design doc or a diff. For brainstorming and PRD writing, multiple goldfish run in parallel with different lenses to generate divergent ideas or research findings the elephant synthesizes.

| Command | When to use |
|---|---|
| `/eg-brainstorm <rough idea>` | Early-stage concept design. Multiple goldfish in parallel (technical / business / UX / contrarian / market research), web search optional, elephant synthesizes a concepts brief. All questions via `AskUserQuestion`. Hands off to `/eg-prd` or `/eg-new-feature` if you pick a direction. |
| `/eg-prd <idea \| feature description>` | Build a thorough PRD: codebase grounding → structured gap-filling via `AskUserQuestion` → deep research with parallel goldfish (web + optional Chrome MCP for logged-in sources) → synthesized PRD. Saves to `notes/prds/`, persists durable nuggets to memory, and/or hands off to `/eg-new-feature`. |
| `/eg-fix-bug <description \| #issue \| URL>` | Bug fix flow: problem doc → goldfish diagnosis check → failing test → fix → `/eg-precommit-review` → test gate. Skips ceremony for trivial diffs. |
| `/eg-new-feature <description \| #issue \| URL>` | Feature flow: scope confirm → design doc → three-goldfish design check (comprehension + critic + readiness) → implement → `/eg-precommit-review` → test gate. Data-leakage risk, reproducibility (seeds), and train/test split integrity are part of the design rubric for this project. |
| `/eg-precommit-review` | Local independent-review loop on the pending diff (`ruff check .` + `pytest`). Replaces back-and-forth with PR bots — by the time the PR opens, the substantive review is already settled. |

You give a one-liner; Claude writes the doc back at you. You don't author docs by hand. Examples:

Backend/data-science project — no browser or simulator surface to drive; verification is tests plus sanity-checking pipeline output on sample data.

Each command stops short of committing. Authorize the commit explicitly when ready. No commit convention is established yet (repo has zero commits as of bootstrap) — plain, imperative subject lines are the default until you set a convention.

## Architecture

Locked in via `/eg-prd` on 2026-09-15 — full reasoning, research, and risk analysis in `notes/prds/big-join-architecture-lock-in-2026-09-15.md`. Executes the chosen "Big Join + The Triage List" concept from `notes/eg-brainstorms/readmission-risk-cv-project-2026-09-15.md`.

**Data pipeline (staged, to protect the "weeks not months" timeline):**
1. **Local proving phase:** generate ~10k-20k Synthea patients locally; run the "Big Join" feature-engineering step as local PySpark (`local[*]` master); all data stays on local disk — no GCP dependency at this stage.
2. **Scale-up phase:** once the pipeline is correctness-proven locally, run the *same* PySpark job (only a config-driven base path changes, not a rewrite) on Dataproc Serverless against GCS-resident data at ~50k-100k patients.
3. **Serving layer:** BigQuery holds only the gold table (patient-encounter features + risk score), written via the `spark-bigquery-connector`'s **direct write method** (BigQuery Storage Write API) — not the indirect GCS-staging-bucket path, to avoid provisioning a bucket purely for the BigQuery load. Raw/intermediate data stays in GCS, never loaded into BigQuery, to stay inside BigQuery's free storage tier.

**Stack:**

| Layer | Choice |
|---|---|
| Compute | PySpark — local mode for dev, Dataproc Serverless for scale-up |
| Warehouse | BigQuery (gold/serving table only) |
| Dependency management | `pip` + `requirements.txt`, generated via `pip-compile --generate-hashes` (pip-tools), installed with `pip install --require-hashes` |
| Python version | **3.12** (downgrade landed 2026-09-17 — see note below) |
| Testing | `pytest` + `chispa` (or PySpark 4.1+'s built-in `assertDataFrameEqual`) for DataFrame-equality assertions; transformation/join logic factored into pure functions so it's testable independent of local-vs-cloud environment |
| Schema handling | Hand-declared `StructType` per Synthea CSV table — never `inferSchema` |

**Python version note (resolved 2026-09-17):** `.python-version` is now pinned to **3.12.11** (landed as the first step of the local-Synthea-generation slice, `notes/eg-new-feature/local-synthea-generation-2026-09-16.md`), downgraded from 3.14 per the architecture PRD's requirement — PySpark's full local-distribution Python 3.14 support only landed in PySpark 4.2.0 (Jul 2026), and Dataproc Serverless's managed-runtime support for 3.14 is unconfirmed. `.venv/` was recreated under the new interpreter alongside the pin.

**Hard constraint carried into future model-training work:** the train/test split for the readmission model must be chronological (by admission/discharge date) and grouped by patient ID — never a random row-level split — per this project's standing reproducibility/leakage-prevention rule (see Collaboration preferences above). **Resolved 2026-09-19 (slice 3, `notes/eg-new-feature/model-training-2026-09-19.md`)** in `src/readmission_risk/models/split.py`: a chronological split at a caller-chosen `--test-start-date` (2023-01-01 for the reference run) that is ALSO patient-disjoint (train rows of any patient who appears in the test window are dropped), with a censoring buffer (`index_stop + 30d < reference_date + 1d`, slice 2's own observability rule applied to positives too, removing the asymmetry slice 2 left) and a label-window purge (train rows whose 30-day outcome window reaches into the test period are dropped). Slice 3 also enforces the leakage rules structurally: every fitted statistic lives in a `Pipeline` fitted on training rows only; inner calibration folds are patient-grouped; `organization_utilization` (a whole-simulation total, not point-in-time) and the constant `provider_specialty` are excluded from the features, and a test fails if any gold column is left unclassified.

**Slice-3 results caveats, carried forward and re-measured on the slice-2b gold table (2026-09-20)** (figures live in the README's "Results and caveats" section and `notes/eg-new-feature/readmission-label-planned-exclusion-2026-09-20-measurements.md`, not here; the slice-3 design doc's own numbers describe the pre-2b all-cause table): (1) the 2023+ test window is NOT a virgin holdout — prototypes scored these models on it during design and the cutoff, feature and (now) label-rule choices were all made from this data (the third such decision); report its metrics as development-set quality, and use the v2 population (generated with a NEW seed and fresh `reference_date`, and sized for statistical power — see (2)) as the untouched validation. (2) After slice 2b the test window holds only **41 positives (2.66%; train 96, 1.50%)** — below slice 3's 50-positive reliability threshold, so its "unreliable" warning fires on the real run by design (the threshold was not lowered) — and intervals are wide. A reason-code-only lookup (test AUC 0.873) is at least as good as either model: logistic regression 0.869, calibrated XGBoost 0.823 (worse than the lookup and than LR, paired intervals excluding 0); Brier skill scores vs the train prevalence are 0.022 / 0.014. The positive rate shifts between train and test (1.50% vs 2.66%), so the models under-predict on average; do not read that as a defect by itself. The label is still reason-concentrated (test window: CABG-history 23 of 41) — same-reason repeats with no procedure evidence that the rule deliberately does not classify as planned; whether to iterate the label again is an open decision. (3) The pre-2b finding that "LR and XGBoost are indistinguishable only under the default training window" no longer holds: XGBoost is worse than LR on ROC-AUC under BOTH the default window and `--train-start-date 20170916` — the latter rests on only 24 training positives and should be read as a direction only. (4) The label now depends on the content of the readmitting stay, not just its start time; on this data 0 of the 118 training rows with an in-window stay have a classifying record dated on or after the test start, but the margin is only ~6 days (2022-12-25T01:59:59Z) and it is a property of this dataset, not a guarantee (tightening slice 3's purge is a follow-up). **Deviations from the MLOps-spine wording above (decisions, not drift):** training reads local Parquet, not BigQuery `to_dataframe()` (BigQuery is the scale-up phase; the loader is one swappable function); `mlflow.autolog()` (one call, spark/pyspark.ml flavors excluded) logs params/in-sample training scoring but the models are logged explicitly with `serialization_format="cloudpickle"` (autolog's default skops format rejects the calibrated XGBoost model) — slice 4 must load them via `readmission_risk.models.tracking.load_logged_model(tracking_dir, run_id)`, needs the same lockfile versions, and gets a pickle-safety warning; `LogisticRegression` is not wrapped in `CalibratedClassifierCV` (natively probabilistic; its calibration is evaluated like XGBoost's). **Known gaps (unchanged conventions, flagged not fixed):** `pyproject.toml` still declares `dependencies = []` (the project's lockfile-only convention), and no CI check verifies that `requirements.txt` still matches `requirements.in`; the earlier gap that `reference_date`/`readmission_window_days` could not be validated against the gold table is **resolved in slice 2b** (`_gold_metadata.json`, checked for exact equality by `train_and_evaluate`; its row/positive-count cross-check cannot detect an edit that preserves both counts — a content fingerprint is a named follow-up). The full list of remaining slice-3 follow-ups (hyperparameter tuning, feature attribution, CI pip cache, a tracked reference-baseline run, fresh-seed v2 validation, the pandas 3 upgrade check, and more) is the design doc's "Out-of-scope follow-ups" section in `notes/eg-new-feature/model-training-2026-09-19.md`.

**Requirement carried into slice 2 (the Big Join feature-engineering design), found empirically 2026-09-17 — resolved 2026-09-19:** local Synthea generation was run with `exporter.years_of_history=0` (full patient history, no truncation) so slice 1 wouldn't pre-judge how much lookback the join needs. This has a real cost — an isolated comparison at the same population/seed showed full history is **~2.6x** the size of Synthea's own 10-year-default export (1.6GB vs 637MB at 1,000 patients), and even the 10-year default extrapolates to ~6.4GB at 10,000 patients, well past the "a few hundred MB" that was informally expected. Two decisions the slice 2 design doc had to make explicitly, not by default — both now resolved and implemented (full reasoning and measurements in `notes/eg-new-feature/pyspark-big-join-2026-09-19.md` and its companion `...-measurements.md`):
1. **History lookback window, resolved as `lookback_years=1` (feature window) + `exporter.years_of_history=10` (regeneration bound).** `lookback_years=1` matches the LACE index's 12-month convention and is empirically supported: a per-calendar-year sparsity analysis of the full-history export found 0.0% of alive patients had zero observations in any calendar year (1916-2025), so a 1-year window isn't degenerate. `years_of_history=10` was chosen (not just because it's Synthea's own default) because it measures to ~2GB at 10,000 patients for the 10 selected tables below — an ~8.5x reduction from the prior 17GB full-history export — while keeping the lookback-window "truncation dead zone" to ~10% of the retained population. Confirmed empirically at BOTH population=1,000 and the real target population=10,000 that active (ongoing) condition/medication/careplan counts are invariant to `years_of_history` (Synthea preserves a patient's full current problem list regardless of history-window setting); only resolved/historical records are pruned.
2. **Table selection, resolved as 10 of Synthea's ~18 exported tables**: `patients`, `encounters`, `conditions`, `medications`, `procedures`, `careplans`, `observations`, `payers`, `providers`, `organizations` (see `TABLES_JOINED` in `src/readmission_risk/pipeline/big_join.py`). `claims.csv`/`claims_transactions.csv` are excluded as billing-line-item exports (confirmed: together ~11GB of the prior 17GB full-history export); `immunizations`/`allergies`/`devices`/`imaging_studies`/`payer_transitions`/`supplies` are excluded as weak/indirect signal for a first-pass readmission model. `generation.py`'s `EXPECTED_CSV_TABLES` was extended from the original 7 to all 10 of these to match; `REQUIRED_NONEMPTY_TABLES` was extended from 2 (`patients.csv`, `encounters.csv`) to 5 (adding `payers.csv`/`providers.csv`/`organizations.csv`) — the other 5 joined tables (`conditions`/`medications`/`procedures`/`careplans`/`observations`) are deliberately allowed to come back empty (warning-only, not a hard failure) per `validate_generation_output`'s existing design — **with one asymmetry added in slice 2b (2026-09-20): the Big Join now hard-fails on an empty `procedures.csv`** (`TABLES_MUST_BE_NONEMPTY`), because the planned-stay flag reads it and an empty file would silently revert the label to (nearly) all-cause; slice 1's `REQUIRED_NONEMPTY_TABLES` still only warns (named follow-up).

**Readmission label (locked 2026-09-19; redefined 2026-09-20 in slice 2b — `notes/eg-new-feature/readmission-label-planned-exclusion-2026-09-20.md`):** an **unplanned** 30-day readmission flag, `is_readmitted` (column name kept; semantics changed; identity `LABEL_DEFINITION = "unplanned_readmission_v1"` in `src/readmission_risk/pipeline/gold_metadata.py`). Inspired by, but not a full implementation of, CMS HRRP's and LACE's shared 30-day convention, which exclude planned readmissions (the CMS specifics are as recalled, not verified — verify before citing). All rules are over inpatient stays: a stay is **planned** if it carries a chemotherapy/radiation procedure (SNOMED 33195004, 367336001, 703423002) — on Synthea data this identifies the lung-cancer treatment cycles that were 72.6% of the old all-cause positives; a stay is a **continuation** if it starts at or before the end of an earlier stay of the same patient (Synthea records one surgical care episode as several overlapping encounters); a stay is **terminal** if no other same-patient stay has `START <= its STOP < that stay's STOP`. Index encounters = inpatient stays with a non-null `STOP` that are neither planned nor non-terminal; label = 1 if the same patient has a stay that is neither planned nor a continuation starting in `(STOP, STOP + 30d]` (upper bound inclusive); an index is excluded entirely (not labeled 0) when the patient died or the export's observation window ended before a readmission could be confirmed absent (applied AFTER labeling). Known residuals (see the design note): same-reason CABG-history/CHF recurrences with no procedure evidence remain positives; features stay stay-level, not episode-level. `build_big_join` also writes `_gold_metadata.json` next to the Parquet (label definition, planned codes, `reference_date`, window, lookback, row/positive and stay-flag counts) and slice 3 **refuses** a gold table without it or with a mismatching `reference_date`/`readmission_window_days`. See `flag_inpatient_stays` / `build_index_encounters` in `src/readmission_risk/pipeline/big_join.py`. (Superseded definition, kept for history in the slice-2 design doc: all-cause, no planned exclusion.)

**MLOps spine (locked 2026-09-15, second `/eg-prd` pass):**
- **Models:** scikit-learn `LogisticRegression` baseline + `XGBClassifier` (XGBoost) challenger, both trained on the BigQuery gold table via `google-cloud-bigquery`'s `to_dataframe()`. Both MUST report calibrated probabilities (`CalibratedClassifierCV` on the XGBoost model) and MUST be evaluated on calibration curve + Brier score alongside AUC — "calibration over raw accuracy" is a project priority given synthetic data, not accuracy/AUC alone.
- **Experiment tracking:** MLflow, **local file-store/SQLite backend for v1** (zero infra, `mlflow.autolog()` covers both models in one call). A hosted GCP tracking server (Cloud Run + Cloud SQL + GCS) is a named **later-phase upgrade**, not v1 scope.
- **Batch scoring (v1):** a single Typer-based CLI script, **no orchestrator** — manual trigger or literal crontab. Built as pure, importable functions (idempotent, overwrites the full prediction partition per run date) specifically so a later Airflow migration wraps it without a rewrite. Airflow (self-hosted, not Cloud Composer — Cloud Composer runs ~$400+/month minimum even idle) is the named later-phase orchestration upgrade.

**Dashboard / team-lead front door (locked 2026-09-15/16, third+fourth `/eg-prd` passes):** **Streamlit** app, **v1 hosted on Streamlit Community Cloud** (free), reading the BigQuery gold table via the plain `google-cloud-bigquery` client. Credentials: a dedicated service account scoped to `roles/bigquery.dataViewer` on the gold dataset only, stored in Streamlit's Secrets manager, never committed. Caching: `st.cache_data(ttl=...)` set to hours (not the docs' 10-minute default) since the gold table only refreshes weekly, bounding query cost under public traffic. The app sleeps after 12h of inactivity on the free tier — mitigated with a scheduled GitHub Actions keep-alive ping so recruiters never see the wake screen. **v2 (named later-phase upgrade):** same Streamlit code, self-deployed via **Dockerfile + Cloud Run** instead of Community Cloud — a differentiated GCP deployment skill addressing the "already shipped Streamlit before" CV-signal concern, without taking on standing BI-tool infrastructure. **Apache Superset (self-hosted) and Preset.io's free tier were both evaluated and explicitly rejected**, including on CV-signal grounds specifically: Superset requires a standing Postgres+Redis+Celery+web-app stack even in its lightest form, and this project's one-opinionated-artifact concept is exactly the use case Superset's actual differentiator (self-serve multi-chart BI exploration) isn't built for — a single-dashboard Superset deployment would likely read as under-justified tool choice rather than a strong signal. Preset's free tier excludes embedded dashboards/API access and hibernates idle workspaces after 30 days.

**Repo hygiene (locked 2026-09-16, fourth `/eg-prd` pass):**
- **Layout:** `src/` layout — one importable package `src/readmission_risk/` with sub-modules per stage (`pipeline/`, `models/`, `scoring/`, `dashboard/`); `tests/` mirrors that structure; `notebooks/` is exploration-only, never production code.
