# Batch scoring (Slice 4: Top-N triage list)

> Terminology: "slice N" names the build stages in the [README Status table](../README.md#status) (1 Synthea generation, 2 PySpark feature join, 2b unplanned label, 3 models, 4 Top-N CLI); "v2 population" is the planned scale-up cohort (see the README Roadmap).

`scripts/score_discharges.py` ranks discharges by predicted risk and prints the Top-N. **It is a demo, not as-of scoring:** it scores discharges that already exist in the gold table, restricted to the rows the chosen model's training run recorded as its held-out `test` partition (`split_assignment.csv`), never the rows it was trained on. Building features for unlabelled recent discharges is a named follow-up. The design, its measurements and its 5-round design check are in [notes/eg-new-feature/batch-scoring-cli-2026-09-20.md](../notes/eg-new-feature/batch-scoring-cli-2026-09-20.md). Since v2 slice 2 the scorer reads the model from a **model bundle**, not from MLflow (see [Model bundles](#model-bundles) below and [the design note](../notes/eg-new-feature/v2-slice2-model-bundle-and-manifest-2026-10-11.md)).

```sh
# Export the two reference runs as bundles (once; prints each bundle id and the champion.json text that would promote it)
make export                                   # logistic regression
make export EXPORT_MODEL=xgboost_calibrated

# Score the held-out discharges of the 30 days ending 2025-06-30 with the champion bundle (deploy/champion.json: since
# v2 slice 7 the logistic regression trained on main_200k, so the gold is v2/main_200k; `make gold-200k` downloads it)
python scripts/score_discharges.py --gold-dir data/gold/main_200k --run-date 20250630

# The v1 (10k) model on its own gold; add --show-observed-outcomes for a sanity check against what actually happened
python scripts/score_discharges.py --gold-dir data/gold/full_run_2b --run-date 20250630 --bundle bundles/75a1448729ef561c596f5e850f5bedce50ed63355ca2de38dc724c635d24eef4 --show-observed-outcomes
```

**Python version.** A bundle is only scored under the Python major.minor its model was trained with (guard 14; the models are cloudpickles). The reference runs in `readmission-risk-v1` were trained on Python 3.14.7 (2026-10-10), so the commands above run in the default environment. The older `readmission-risk-2b` runs (Python 3.12.11, trained on the gold table before it gained the `label_horizon` column) are kept only as history: the fingerprint guard refuses them against the current table, and guard 14 refuses them under 3.14. To score a run trained on Python 3.12 against a matching gold table, first export it to a bundle in the default environment (`python scripts/export_bundle.py --run-id <id>`; exporting never unpickles, so it works under 3.14), then score that bundle from a Python 3.12 environment (any Python 3.12 interpreter, e.g. `pyenv shell 3.12.11` or Homebrew's `python3.12`) outside the repository, with the same prerequisites as [setup.md](setup.md) (on macOS `brew install libomp` for XGBoost), run from the repository root with `--bundle bundles/<id>`. Since 2026-10-12 the lockfiles are compiled under Python 3.14; installing them on 3.12 was verified on that date, not continuously. If pip reports a missing hash or `pip check` fails, the 3.14 compile dropped a dependency that only 3.12 needs. This 3.12 recipe is not exercised by CI since 2026-10-11; CI tests only the pipeline subpackage on 3.12:

```sh
python3.12 -m venv ~/.venvs/readmission-py312 && source ~/.venvs/readmission-py312/bin/activate
pip install -e .
pip install --require-hashes -r requirements.txt -r requirements-linux-extras.txt
pip install --require-hashes -r requirements-dev.txt
```

or retrain under 3.14 with a fresh `--experiment-name` and export that run.

| Flag | Meaning |
|---|---|
| `--gold-dir`, `--run-date` (required) | the gold table (with `_gold_metadata.json`) and the last day (`YYYYMMDD`, UTC) of the window |
| `--window-days` | window length in UTC calendar days; default the gold table's readmission window (30). A row is in the window iff `run_date - (W-1) days 00:00Z <= index_stop < run_date + 1 day 00:00Z` |
| `--bundle` / `--champion` | the model source: an explicit bundle directory, or a champion pointer to follow; with neither, `deploy/champion.json` relative to the current directory. Mutually exclusive |
| `--top-n` | how many rows to print (default 10); the whole ranked batch is written regardless |
| `--show-observed-outcomes` | opt-in: prints how the observed readmissions line up with the Top-N, joined after scoring and never written to the file |
| `--output-dir` | default `data/predictions` (gitignored) |

**Output.** `<output-dir>/run_date=YYYYMMDD/predictions.parquet`, one file per run date, replaced as a unit (temp file + atomic rename): re-running a run date overwrites the whole partition, so scoring the same date with another bundle replaces the first one's file. Columns, in order: `as_of_date`, `rank` (1 = highest risk; ties in `risk_score` are broken by `encounter_id` ascending, so ranks are always distinct), `is_top_n`, `patient_id`, `encounter_id`, `discharge_time` (UTC), `admission_reason_code`, `admission_reason_description`, `risk_score`, `model_bundle_id` (the bundle that scored the partition), `model_run_id` (the MLflow run the bundle was exported from), `model_name`, `top_n`, `scoring_window_days` (the trailing-window length; not the 30-day label window), `partition` (always `test`), `label_definition`, `gold_fingerprint`, `gold_reference_date`. There is no label column. The demo notice and `readmission_risk.schema_version` (`"2"` since v2 slice 2, which added `model_bundle_id`) are stored in the file's schema metadata. Reading the parent directory (`pd.read_parquet("data/predictions")`) works and adds a categorical `run_date` column, provided every partition has the same schema version: re-score or delete partitions written before v2 slice 2 rather than mixing them with new ones.

**What is refused (exit 1, `ERROR:` on stderr, nothing written).** A window that contains any discharge that is not a held-out row of the chosen model (a training row, a row dropped by the split, or a censoring-buffer row) is refused rather than silently truncated. So is a window that reaches past the **observation horizon** (the end of the reference date, i.e. the reference date + 1 day at 00:00Z, minus the 30-day label window; the window must end by this instant: 2026-09-13 00:00Z for the champion on `main_200k`, 2026-08-18 00:00Z for the v1 model on `full_run_2b`, so the last valid run dates are 20260912 and 20260817): the gold table keeps a non-readmitted discharge only once its outcome window has closed, so later windows would hold readmitted discharges only, and no comparison against the rows that do exist could notice the rest are missing. With a 30-day window, the champion on `main_200k` (since v2 slice 7) has 1,240 valid run dates between `20230323` and `20260912` (batches of 629-774 rows, median 705; not contiguous, because a window that holds one of the few 2023 rows the split assigned to no partition is refused); the v1 model on `full_run_2b` has 1,287, `20230208` through `20260817` (batches of 21-49 rows, median 35). Before any model is loaded, integrity checks verify the bundle (the champion's sha256 pin on `manifest.json`, the content-hash `bundle_id`, every file's size and sha256, and the manifest's shape), and then 14 guards check the bundle's manifest against the gold table: it must come from a finished, non-deleted `train_and_evaluate` run, trained on **exactly this gold table** (fingerprint) and label definition, with matching `reference_date` / `readmission_window_days`, the same library versions as the lockfile (the model is a cloudpickle), the same Python major.minor (from the run's `python_version` tag, or for runs trained before that tag existed, the version MLflow wrote into the logged model's `MLmodel`, both copied into the manifest at export), the current feature contract and signature (names, types, all required), a consistent train/test assignment, and a model that belongs to the run.

## Model bundles

A bundle is an immutable, content-addressed directory, `bundles/<bundle_id>/`, holding `manifest.json`, `model.pkl` (the MLflow logged model's cloudpickle, byte for byte) and `split_assignment.csv` (the run's train/test assignment, byte for byte). `bundle_id` is the sha256 of the manifest's canonical JSON without its own id; the manifest lists every other file's sha256, and carries no timestamp, so exporting the same run again gives the same id (and `status: already existed`). A bundle is never overwritten. MLflow remains the experiment record; the scorer never imports it.

- **Export:** `python scripts/export_bundle.py --run-id <id>` or `--experiment-name <name> --model <model>` (`make export`, with `EXPERIMENT` and `EXPORT_MODEL`). It refuses a run whose model or artifacts it cannot read; everything else is recorded in the manifest and judged by the scorer. Re-running `train_models.py` under an existing experiment name makes `--model` ambiguous (it refuses and lists the run ids): use a fresh `--experiment-name` per training run, or pass `--run-id`.
- **Champion:** `deploy/champion.json` names the live bundle as `{"bundle_uri", "sha256"}`, where `sha256` pins that bundle's `manifest.json`. Promotion is a PR that edits it (the exporter prints the text); rollback is `git revert`. A relative `bundle_uri` is resolved against the current directory; a `gs://` one (since v2 slice 4 the champion lives in the private bundle bucket) is read from Cloud Storage, which needs Application Default Credentials that can read the bucket (`gcloud auth application-default login`; as the operator, add `--impersonate-service-account scorer@synthea-readmission-risk.iam.gserviceaccount.com`). **Offline:** pass `--bundle bundles/<id>` and a local `--gold-dir`; nothing then touches the network.
- **Bundles in GCS:** `--bundle` and the exporter's `--bundles-dir` accept `gs://` URIs. The reader needs `storage.objects.list` and `get` on the bucket; the exporter uploads create-only (`if_generation_match=0` on every object, `manifest.json` last, no retries), so an existing bundle is reported as "already exists" and never replaced. Run it as `bundle-writer` (`--impersonate-service-account bundle-writer@synthea-readmission-risk.iam.gserviceaccount.com`); that account cannot read, so verify an upload with a reader ([setup.md](setup.md#scoring-into-bigquery-v2-slice-4)).
- **Trust:** the model is a cloudpickle, which can run code when loaded, so it is unpickled only after every check has passed. Behind the champion, integrity is anchored in the committed sha256 pin. A bundle passed with `--bundle` is anchored only in its own self-consistent hashes: anyone who can write it can recompute them, so treat bundles as trusted local input, like the MLflow store.
- **Fresh clone:** bundles are gitignored, and the copies uploaded in v2 slice 3 live in a private bucket, so the committed champion names a bundle that only the author can read or reproduce (`make export` from the author's MLflow store). Anyone else trains, exports and scores their own: `make train TRAIN_EXPERIMENT=<x>`, then `make export EXPERIMENT=<x>`, then `make score SCORE_GOLD_DIR=<the gold you trained on, e.g. data/gold/full_run_2b> SCORE_ARGS="--bundle bundles/<id>"` with the id the export printed.
- **Deleting a bundle:** bundles are read-only on purpose, so `rm -rf` and `git clean -fdx` fail on them; run `chmod -R u+w bundles/<id> && rm -rf bundles/<id>` (or `chmod -R u+w bundles` before a `git clean`).
- **Portable form (manifest schema 2, v2 slice 6c, FR0.3):** a cloudpickle is loadable only under the exact library pins and Python minor it was written with (guards 8 and 14), so the two frozen v1 models were exported once more as **schema-2 bundles** that also carry the model as data: `portable.json` (preprocessing parameters, one-hot categories, logistic-regression coefficients, sigmoid calibrator `a`/`b` per fold), XGBoost's own `portable_fold_<k>.ubj` boosters, and `portable_reference.csv` (the parity inputs, i.e. the 1,539 v1 test rows plus 325 deterministic probe rows covering every fitted category, an unseen value and `MISSING`, with the pickle's outputs on them). `model.pkl` and `split_assignment.csv` are byte-identical to the source bundle's. The export refuses to write anything unless the portable predictor, loaded from the exact bytes it writes, reproduces the pickle with a maximum absolute difference of exactly 0; both v1 models do (bundles `fb44c38910b4…` for logistic regression and `bf66d1cb272b…` for XGBoost, from `75a1448729ef…` and `30009d198070…`). `make export-portable SOURCE_BUNDLE=bundles/<schema-1 id>` (or `python scripts/export_portable_bundle.py --source-bundle …`) runs it; the source must be local and must pass the scorer's full validation on `--gold-dir`. The scorer accepts schema 1 and 2 and checks the portable files' sha256 and the manifest's `portable` block, but still scores from `model.pkl`; the champion is a schema-1 bundle (since v2 slice 7 the 200k logistic regression, which has no portable form). `readmission_risk.portable.predictor.read_portable_bundle(uri)` plus `verify_reference(model, reference)` re-check parity against the stored reference without the pickle or the gold table. **Known risk:** that proof is bit-exact, and bit-exactness can depend on the numeric libraries (numpy's BLAS, scipy's `expit`, xgboost) and on the batch layout (measured: batches of 1-17 rows give different last bits than the same rows in a larger batch), so it is re-checked per reference segment exactly as it was written; a mismatch means "this environment does not reproduce the frozen model", and any tolerance would be a requirement change. The proof also covers the reference rows only. **Measured (measured 2026-10-18):** on macOS the re-check passes with newer numpy (2.5.4), pandas 3, xgboost 3.3.0 / scipy 1.17.1 and without scikit-learn and pandas; xgboost 3.0.5 (older than the writer) misreads the newer booster files (`base_score` falls back to 0.5) and the re-check correctly refuses (max abs diff 0.975). On Linux (arm64 and x86-64, same pins) the portable form equals the pickle run there exactly, but both differ from the macOS-written reference (logistic regression ≈3e-16, XGBoost 2.6e-9), so `verify_reference` refuses on Linux: the bit-exact re-check is, today, a macOS-only proof (follow-up in the design note). Design: [notes/eg-new-feature/v2-slice6c-portable-v1-export-2026-10-17.md](../notes/eg-new-feature/v2-slice6c-portable-v1-export-2026-10-17.md).
- **Partial upload of a schema-2 bundle:** a schema-2 bundle is 5 (logistic regression) or 10 (XGBoost) objects, uploaded create-only with no retries and `manifest.json` last. If an upload fails part-way, the prefix has no `manifest.json` and the writer can never complete it (re-runs report "already exists"). Recovery: as the owner's own identity, list the prefix, delete it with `gcloud storage rm --recursive --all-versions gs://synthea-readmission-risk-bundles/<id>/` (the same recipe as [setup.md](setup.md#scoring-into-bigquery-v2-slice-4)) and re-run the upload. A GCS error other than "already exists" ends the export CLI with a traceback, as `export_bundle.py` does.

**Read the list with these limits in mind** (the CLI prints the first one on every run):
- **Weak models, already-used rows.** The models do not beat a reason-code-only lookup (see [Results and caveats](results.md)), so the Top-N mostly ranks by admission reason: with the champion (the 200k logistic regression), the `20250630` batch of 675 has a Top-10 of seven aortic-valve-stenosis, two CABG-history and one aortic-regurgitation stays (`risk_score` 0.6382 down to 0.1391); with the v1 model on `full_run_2b`, the batch of 42 had six CABG-history stays, two NSTEMI and two drug-abuse admissions (0.0816 down to 0.0149). Neither test window is a virgin holdout: the 10k one was used while designing the models and the label, the 200k one by the promotion gate. Read `risk_score` as a ranking, not an absolute risk.
- **Membership is not as-of.** Which gold rows exist depends on whole-export information (the terminal rule and the death/censoring keep-rule), so a real as-of list would contain rows this one omits, notably patients who died within 30 days.
- **Simulated run date.** Patients already readmitted before the run date still appear, and the same discharge appears in up to W consecutive run-date partitions.
- **`--show-observed-outcomes` counts are small** (the champion's `20250630` batch has 11 readmissions in 675 discharges, 2 of them in the Top-10; the v1 batch had 1 in 42): they are a sanity check, not evidence.
- The notice text was revisited in v2 slice 7 and holds for both the 10k and the 200k model (each window was already used to select models); revisit it again before real as-of scoring.

A five-row sample of this output (with the same demo caveats) is in the [README](../README.md#example-output); `scripts/make_readme_assets.py` regenerates it from a saved predictions file.

## Scoring into BigQuery (v2 slice 4)

`scripts/score_to_bigquery.py` (`make score-bq`) runs the same scorer, then serves its rows from BigQuery: dataset `serving` holds `predictions` (partitioned by `as_of_date` = the run date, a partition filter required) and `scoring_runs` (one row per attempt). Design: [the design note](../notes/eg-new-feature/v2-slice4-score-to-bigquery-2026-10-11.md).

```sh
# As the operator (impersonating the scorer service account; needs ADC). The gold table is read from GCS.
make score-bq RUN_DATE=20250630
# Prove every data test fires on a seeded bad row (PRD M5), on a run date published by slice-7 code (PRED-11 needs
# gold_fingerprint_definition, which older rows lack); M5_RUN_DATE defaults to 20230417
make m5-check
# The same for serving.monitoring, on synthetic rows (v2 slice 7)
make m5-monitoring
```

- **Write, audit, publish.** The rows are loaded into a short-lived table in dataset `scratch`, the [`predictions.sql`](../src/readmission_risk/warehouse/sql/predictions.sql) data tests run on them there, and only if they pass does one transaction replace the run date's rows in `serving.predictions`. A run whose tests fail never changes what is served. Re-running a run date replaces its rows as a unit (the v1 semantics); every live row carries the `scoring_run_id` that published it.
- **Data tests.** [`predictions.sql`](../src/readmission_risk/warehouse/sql/predictions.sql) (11 assertions since v2 slice 7, which added PRED-11 for the new `gold_fingerprint_definition` column), [`scoring_runs.sql`](../src/readmission_risk/warehouse/sql/scoring_runs.sql) (7, run on the table's state before each attempt) and [`monitoring.sql`](../src/readmission_risk/warehouse/sql/monitoring.sql) (12, v2 slice 7) are BigQuery `ASSERT` scripts; every assertion is labelled `AS '<ID>: <message>'`, and a NULL counts as a failure. `make m5-check` gives every assertion its own copy of real rows with one seeded bad row and checks that exactly that assertion fails.
- **Exit codes.** 0 succeeded and recorded; 1 refused (`ERROR:`, the scorer's usual refusals); 3 data tests failed (`DATA TESTS FAILED: <ID>: …`, nothing published); 4 succeeded but the `scoring_runs` row could not be written; a failed run (a BigQuery or storage error) ends with its traceback. Every attempt that has a BigQuery client is recorded, refusals included. In GitHub Actions the run also writes a job summary.
- **Cost.** Every query carries `maximum_bytes_billed` (100 MiB); the tables are tiny (a few hundred rows per run date), so a run bills a few tens of MB of the 1 TiB monthly free tier.
- **Who can do what.** The `scorer` service account reads the bundle and gold buckets, owns `scratch`, and on `serving` holds only a custom role on the two tables (`tables.get`, `getData`, `updateData`): it cannot create, drop or alter tables there. It runs keylessly from [score.yml](../.github/workflows/score.yml) (dispatch) and from the monitoring tick's score job in [monitor.yml](../.github/workflows/monitor.yml) (v2 slice 7, a 7-day window per simulated week), both on `main`; both share one concurrency group, so a `score.yml` run never overlaps a tick.
